Major rework since the first review pass:
  • Patterns changed from ^lp-interop- (single hyphen) to three double-hyphen patterns: ^lp-chaos--, ^lp-interop--, ^lp-ocp-compat--. The -- convention distinguishes prefix separators from word separators within the prefix.
  • Patterns declared as pre-compiled []*regexp.Regexp (no init() needed)
  • New GetSuiteID replaces CheckForDynamicSuite — now checks both the static list and patterns via isSuiteImportable
  • findSuite in prow.go drastically simplified — delegates entirely to db.GetSuiteID

Overview

Adds pattern-based dynamic suite creation so that suite names matching configurable regex patterns are auto-created in the database at load time. Three lp-* prefixes are currently configured. Also introduces isSuiteImportable as a gating function that checks both the static testSuites list and the dynamic patterns before any DB interaction. Refactors populateTestSuitesInDB and findSuite to reuse the new helpers.

Files Changed

  • pkg/dataloader/prowloader/prow.go — findSuite: removed inline DB query, now delegates entirely to db.GetSuiteID
  • pkg/db/suites.go — new GetSuiteID, isSuiteImportable, getOrCreateSuite; refactored populateTestSuitesInDB; pattern list with three compiled regexps
  • pkg/db/suites_test.go — unit tests for pattern matching

What's Good

GOOD Clean layered design
GetSuiteID → isSuiteImportable → getOrCreateSuite is a clean pipeline. Each function has a single responsibility: gate, check, act.
GOOD findSuite drastically simplified
The prow loader no longer contains any suite DB logic — just a cache wrapper around db.GetSuiteID. This is a much better separation of concerns than the original.
GOOD isSuiteImportable as pure function
This is exactly the right extraction — a testable, DB-free function that encapsulates all "should we care about this suite?" logic.
GOOD Inline regexp.MustCompile
Cleaner than the previous init() + separate string slice approach. Compile errors still surface at process start.

Issues & Suggestions

ISSUE Behavioral change: findSuite now rejects unknown suites that exist in DB

pkg/dataloader/prowloader/prow.go:1183-1186

The old findSuite looked up any suite by name in the DB and returned its ID if found. The new code calls db.GetSuiteID, which first runs isSuiteImportable — if a suite exists in the database but is not in the static list or pattern list, GetSuiteID returns nil without ever querying the DB.

This means tests from suites that were previously imported (before they were removed from the allowlist, or added manually) will silently stop getting a suite ID assigned. This may be intentional, but it's a significant behavioral change that should be called out explicitly.

ISSUE Misleading log message: "retrieved" vs "created"

pkg/db/suites.go:137-139

FirstOrCreate sets RowsAffected to 1 when it creates a new record, and 0 when it finds an existing one. The log message says "retrieved test suite" but it actually fires only on creation. This is the opposite of what the message says.

Change the log message to "created new test suite" (matching the old behavior) or remove it since populateTestSuitesInDB doesn't need per-suite logging.
MINOR Test still duplicates matching logic instead of calling isSuiteImportable

pkg/db/suites_test.go:95-101

The test re-implements matching with its own != "" && re.MatchString loop. Now that isSuiteImportable exists as a pure, DB-free function, the test should call it directly. This would also catch suites that match via the static list, making the test more accurate.

Replace the inline loop with a call to isSuiteImportable(tt.suiteName). Note that the "openshift-tests" test case would then need shouldMatch: true since it's in the static list.
MINOR Test case name contradicts its expected result

pkg/db/suites_test.go:79-83

The test case is named "no pattern match - only prefix no suffix" with input "lp-interop--" and shouldMatch: true. The name says "no pattern match" but the expectation is that it does match. Rename to something like "matches pattern even with empty suffix".

MINOR FirstOrCreate race condition (carried from rev 1)

pkg/db/suites.go:117

FirstOrCreate without a unique constraint on suites.name could insert duplicates under concurrent access from multiple ProwLoader instances. The old code used clause.OnConflict{UpdateAll: true}. The fallback read (now fixed in 75c3cd4b) mitigates this partially.

Author's position (from PR discussion): The prow loader runs on a cron schedule. New suites are rare, and a transient failure will be picked up on the next run. This is an acceptable trade-off for code simplicity.

Acknowledged as acceptable. If you want belt-and-suspenders, a unique index on suites.name would make the fallback path unnecessary entirely.

PR Discussion Notes

Key points from the review thread worth being aware of:

  • @oharan2 suggested populateTestSuitesInDB should call GetSuiteID (the wrapper) instead of getOrCreateSuite directly. @etirta disagreed: populateTestSuitesInDB is only for pre-seeding with concrete names, so isSuiteImportable checks are unnecessary there.
  • @etirta explained the -- double-hyphen convention: it distinguishes the prefix separator from word separators within the prefix itself (e.g., lp-ocp-compat has hyphens in the prefix, -- marks where the prefix ends).
  • @neisw on race conditions: the loader runs on a cron schedule, new suites are rare, and the next cron invocation retries naturally. Complexity not warranted.
  • @etirta left a nit about the naming convention comment accuracy (commit 4fe9c466 addressed this).
